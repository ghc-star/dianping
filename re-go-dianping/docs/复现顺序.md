# Go 点评复现顺序

按依赖关系逐步实现接口：用户与会话 → 商铺 → 笔记 → 关注与 Feed → 图片与 GEO → 优惠券与秒杀 → 运行能力。每个接口先写能运行的版本，再补边界和并发处理。

本文是实现路线，不代表所有接口已经完成或通过验证。已经写过的接口按验收项复查，不必重写。近期已练习的内容包括商铺详情、验证码登录、会话、退出、发送频率限制和用户公开信息查询。

参考：[原项目 API 文档](../../go-dianping/docs/API.md)、[原项目实现指南](../../go-dianping/docs/IMPLEMENTATION_GUIDE.md)。文中的 `:id` 是 Gin 路径参数，例如请求 `/user/1`。

## 一、每个接口的实现顺序

1. 明确请求方法、路径、参数、返回数据、是否需要登录。
2. 需要新表时先建表，再写 `model`；修改结构体不会自动修改数据库。
3. 需要接收 JSON 时写请求 DTO；需要限制返回字段时写响应 DTO。
4. 写 Repository，只处理数据库查询、更新和事务。
5. 写 Service，组织业务规则、Repository 和 Redis 操作。
6. 写 Handler，解析参数、调用 Service、返回响应。
7. 在 `handler/router.go` 注册路由，在 `main` 中组装依赖。
8. 验证正常请求、非法输入、资源不存在、未登录和依赖故障。

```text
main：连接 MySQL、Redis，创建 Repository、Service、Handler
    ↓
router：将请求方法和路径绑定到 Handler
    ↓
Handler：解析请求 → Service：业务处理 → Repository：数据库操作
```

纯 Redis 功能（例如签到）不必额外添加 Repository。请求 Context 沿调用链传递，数据库和 Redis 客户端在启动时创建并复用。

### 接口约定与常见错误

- 成功：`{"success":true,"data":...}`；无数据时可以省略 `data`。
- 失败：`{"success":false,"errorMsg":"..."}`。
- 练习版使用：参数错误 `400`、未登录 `401`、资源不存在 `404`、频率限制 `429`、系统错误 `500`、暂时不可用 `503`。
- 原项目部分业务错误使用 HTTP 200；以后接原前端时统一契约。
- 受保护接口请求头使用 `authorization: TOKEN`。当前练习中间件直接读取 Token，不加 `Bearer `。
- Gin 根据“请求方法 + 路径”匹配接口，`GET /user/me` 不能用 POST 请求。
- ID 统一使用 `int64`，解析后检查 `id > 0`；返回错误后立即 `return`。
- 用户表是 `tb_user`，不要误写成 `users` 或 `tb_users`。
- `Scan` 无记录时应检查 `RowsAffected`；不能假设它会返回 `gorm.ErrRecordNotFound`。
- 已有 `FindUser` 等方法名可以继续使用，不必为了和本文示意名字一致而重命名。

## 二、用户与会话

### 0. 先复查已经练习的接口

| 接口 | 登录要求 | 验收要求 |
|---|---|---|
| `POST /user/code?phone=...` | 否 | 六位验证码，120 秒有效；同一手机号 60 秒内不能重复获取；只在开发日志打印 |
| `POST /user/login` | 否 | 校验并消费验证码；新手机号自动注册；生成随机 Token；保存会话失败不能返回成功 |
| `GET /user/me` | 是 | 无需路径参数和请求体；从 Token 确定当前用户；不返回密码和手机号 |
| `POST /user/logout` | 是 | 删除当前 Token 会话，旧 Token 再访问受保护接口返回 401 |

验证码登录不需要单独注册接口：仅获取验证码不会注册，首次验证码登录才创建用户。手机号必须有唯一索引；同一验证码不能重复消费。

当前练习使用 JSON + Redis String 保存会话，原项目使用 Hash。读取方式必须和保存方式一致。会话滑动续期 30 分钟，Redis 故障应与未登录区分。

### 1. GET /user/:id：查询用户公开信息

**需要登录。** 这个接口和商铺查询相似，适合巩固分层。

先写：

```text
Repository.UserByID(ctx, id) → 查询 tb_user
Service.UserByID(ctx, id)    → 转成 UserDTO
Handler.ByID(c)             → 读取并校验路径 id
路由                       → 注册 GET /user/:id 到 auth 组
```

返回示例：

```json
{
  "success": true,
  "data": {
    "id": 1,
    "nickName": "新用户",
    "icon": ""
  }
}
```

第一版验收：

- 能查询自己和其他存在的用户。
- 拒绝非正整数 ID。
- 不返回手机号、密码。
- 数据库故障和用户不存在分开处理。

练习版可以用 404 表示不存在；原项目这里返回成功但没有用户数据。暂时不加用户缓存。

### 2. GET /user/info/:id：查询详细资料

**需要登录。**

先写：

1. 建立 `tb_user_info`，用 `user_id` 关联用户。
2. 定义 `UserInfo`，包含城市、简介、生日等资料字段。
3. Repository 按 `user_id` 查询。
4. Service 转为适合展示的 DTO，Handler 返回资料。

后面补充：用户存在但没有资料记录的情况、返回字段控制、日期格式统一。原项目没有相应的资料编辑接口，可以先插入练习数据完成查询。

### 3. 登录昵称与修改昵称：练习扩展

这部分是后来增加的练习需求，原项目没有独立的修改昵称接口。

先扩展 `POST /user/login` 的请求：

```json
{
  "phone": "13900000009",
  "code": "123456",
  "nickName": "小郭"
}
```

- `nickName` 表示展示昵称，登录身份仍由手机号和验证码确认。
- 校验和去除首尾空白在消费验证码之前完成。
- 新用户使用提交的昵称；未提供时使用默认值“新用户”。
- 已有用户登录时保留原昵称，不因登录请求覆盖资料。

然后新增 `PUT /user/nickname`，需要登录：

```json
{
  "nickName": "小郭"
}
```

实现顺序：DTO → Repository 更新 `nick_name` → Service 校验 1～32 个字符 → Handler 从当前会话取用户 ID → 注册路由。

后面补充：昵称修改后的展示一致性。练习版可让 `/user/me` 根据会话 ID 查询数据库中的最新 DTO；不要直接返回 Redis 中的旧昵称。相同昵称重复提交应允许成功；也要区分目标用户已经不存在，不能只凭更新零行判断用户不存在。

验收：无 Token 返回 401，空白或过长昵称被拒绝；不能指定其他用户 ID；修改后 `/user/me` 和 `/user/:id` 显示新昵称。

### 4. PUT /user/password：设置密码，再扩展密码登录

**需要登录。** 请求示例：

```json
{
  "password": "example123"
}
```

先写：

1. 从中间件取当前用户 ID。
2. 校验密码长度为 8～72 字节。
3. 使用 bcrypt 生成哈希。
4. Repository 更新当前用户的 `password`。

第一版就保证：数据库存哈希，不允许客户端指定其他用户 ID，日志和响应不包含密码。

然后扩展 `POST /user/login`：

```text
传验证码 → 验证码登录，允许首次注册
传密码   → 查询已有用户 → bcrypt 校验 → 创建会话
```

登录 DTO 不再无条件要求验证码，而由业务校验至少提供一种凭证；明确同时提供两种时的规则。密码登录不自动注册用户。

后面补充：密码尝试次数限制；手机号不存在和密码错误使用相同对外提示。验证码登录与密码登录复用 Token 生成和会话保存逻辑。

### 5. POST /user/refresh：主动续期，可选

**需要登录。** 中间件完成续期后返回：

```json
{
  "success": true,
  "data": {
    "ttlSeconds": 1800
  }
}
```

验收：过期 Token 不会被重新激活。已有滑动续期时，这个接口可以晚些实现。

### 6. POST /user/sign 与 GET /user/sign/count：签到

两个接口都需要登录。

| 接口 | 第一版 | 后面补充 |
|---|---|---|
| `POST /user/sign` | 获取当前用户，用 Redis Bitmap 标记今天已签到 | 固定业务时区，验证重复签到 |
| `GET /user/sign/count` | 读取截至今天的签到位，从今天往前统计连续天数 | 月初、月末、今天未签、时区跨日 |

```text
key：practice:sign:用户ID:202609
offset：日期 - 1
```

先实现与原项目一致的“本月内连续签到”规则。今天没有签到返回 0；连续天数不是本月累计签到数，也不跨月累计。先完成 SETBIT，再实现 BITFIELD 与连续位统计。

## 三、商铺功能与缓存

先做查询和写入，再处理复杂缓存问题。

| 顺序 | 接口 | 登录要求 | 第一版 | 后面补充 |
|---|---|---|---|---|
| 1 | `GET /shop-type/list` | 否 | 查询类型表，按排序字段返回 | Redis 缓存类型列表 |
| 2 | `GET /shop/of/type?typeId=1&current=1` | 否 | 按类型查询、数据库分页 | 经纬度查询、GEO 距离排序 |
| 3 | `GET /shop/of/name?name=火锅&current=1` | 否 | 名称模糊查询、分页 | 页码校验、稳定排序、查询性能 |
| 4 | `POST /shop` | 是 | 创建商铺、返回 ID | GEO 索引维护、字段校验完善 |
| 5 | `PUT /shop` | 是 | 更新数据库后删除详情缓存 | 并发回填保护、GEO 更新 |

先扩充简化的 `Shop`，例如类型、经纬度等；同步调整数据库字段。基本必填值和格式校验应在第一版完成。

修改时必须支持零值：

```json
{
  "id": 1,
  "score": 0
}
```

用指针 DTO 字段区分“没传”和“传了零”，再构造更新 map，避免 GORM 忽略结构体零值。

已有 `GET /shop/:id` 缓存按以下顺序增强：

1. **空值缓存**：不存在的商铺缓存短时间，避免反复查库；数据库故障不能作为空值缓存。
2. **TTL 随机偏移**：减少大量缓存同时过期。
3. **singleflight**：同进程内合并同一商铺的并发回源。
4. **分布式锁**：多个实例争抢缓存重建权；使用唯一 token 和 Lua 比较后解锁，等待有上限。
5. **逻辑过期与后台刷新**：热点缓存过期可先返回旧值，后台任务有并发上限和退出机制；冷数据仍须同步加载。
6. **版本保护**：阻止更新前开始的旧查询，在更新后回填旧数据。

前两项完成后可以继续其他业务，后面的并发优化单独练。验证冷缓存、重复查询、不存在、并发回源、更新零值和旧值回填场景。

准备 `tb_blog`、`model.Blog`、发布 DTO、Repository、Service 和 Handler。

| 顺序 | 接口 | 登录要求 | 第一版 | 后面补充 |
|---|---|---|---|---|
| 1 | `POST /blog` | 是 | 发布笔记，验证商铺存在 | 图片关联、Feed 投递 |
| 2 | `GET /blog/:id` | 是 | 查询笔记与作者公开信息 | 当前用户是否点赞 |
| 3 | `GET /blog/of/me?current=1` | 是 | 按当前用户分页查询 | 稳定排序 |
| 4 | `GET /blog/of/user?id=1&current=1` | 是 | 按指定用户分页查询 | 批量补齐展示信息 |
| 5 | `GET /blog/hot?current=1` | 否 | 按点赞数分页查询 | 批量查作者、当前用户点赞状态 |
| 6 | `PUT /blog/like/:id` | 是 | 点赞，再调用则取消点赞 | Redis 排名、并发验证 |

```text
客户端传：商铺 ID、标题、正文、图片
服务端决定：作者 ID、笔记 ID、初始点赞数
```

不能让客户端指定作者身份。

点赞第一版就需要：

- 持久化点赞明细表，唯一约束 `(blog_id, user_id)`。
- 在事务中同时修改关系与点赞计数。
- 串行化同一笔记的并发点赞切换，避免计数错误。
- 拒绝给不存在的笔记点赞。

随后用 ZSet 保存点赞时间排名，读取最早点赞的用户（原项目取前 5 人）。数据库保留完整关系，Redis 投影可以重建。

公开热门接口若要显示“我是否点赞”，把认证拆成可选身份识别与必须登录检查。游客仍可读取热门列表。

验收：发笔记后能查询；分页稳定；同一用户点赞再取消恢复原状态；并发后计数与明细一致；批量查作者避免每条笔记都单独查一次用户。

## 五、关注、共同关注与 Feed

### 1. 先实现关注关系

以下接口都需要登录。

| 顺序 | 接口 | 第一版 | 后面补充 |
|---|---|---|---|
| 1 | `PUT /follow/:id/:isFollow` | true 关注、false 取消，保存数据库关系 | 同步 Redis Set |
| 2 | `GET /follow/or/not/:id` | 查询是否存在关注关系 | 视需要优化查询 |
| 3 | `GET /follow/common/:id` | 查询共同关注的人 | 使用 Set 交集，支持缓存重建 |

基本约束：不能关注自己，目标必须存在，`(user_id, follow_user_id)` 唯一。重复关注只有一行，重复取消不报业务错误。

### 2. 再实现关注 Feed

```http
GET /blog/of/follow?lastId=时间戳&offset=0
```

需要登录，按顺序实现：

1. 发布笔记后查找作者的粉丝。
2. 将笔记 ID 写入粉丝的 Redis ZSet 收件箱，以时间戳排序。
3. Feed 接口读取收件箱。
4. 根据笔记 ID 查询 MySQL，并保持 Redis 中的顺序。
5. 实现时间戳加 offset 的滚动分页。

同一个时间戳跨页时，offset 需要累计；跨到新的时间戳再按新边界计算。

第一版同步投递用于理解流程，仍可能出现数据库保存成功而 Redis 投递失败。后面补事务 Outbox（数据库中的待投递记录）：

```text
同一个数据库事务：保存笔记 + 保存待投递记录
    ↓
后台读取待投递记录
    ↓
写入 Redis
    ↓
标记投递完成
```

验收：

- 同一毫秒多篇笔记，固定数据集翻页不重复、不遗漏。
- Redis 暂时不可用，恢复后可以补投。
- 重投同一笔记不会产生重复成员。
- Redis 收件箱丢失后能够重建。

迟到投递可能落到已翻过的游标之前，需要刷新第一页；不能把动态 Feed 说成固定快照。

## 六、图片上传与附近商铺

两组功能相对独立，可穿插在笔记模块前后。

| 接口 | 登录要求 | 第一版 | 后面补充 |
|---|---|---|---|
| `POST /upload/blog` | 是 | 接收图片，生成服务端文件名，返回路径 | 存储抽象、对象存储 |
| `DELETE /upload/blog/delete` | 是 | 删除本人上传的图片 | 清理未被笔记引用的文件 |
| `GET /shop/of/type` 坐标分支 | 否 | 有 x/y 时用 GEO 查附近商铺，返回距离 | 新增、移动、换类型时维护索引 |

图片接口第一版就校验大小与实际图片类型。删除时验证归属与路径范围，不直接把用户输入当成本地删除路径。

GEO 实现顺序：

```text
数据库准备经纬度
    ↓
按商铺类型建立 Redis GEO 索引
    ↓
搜索附近商铺 ID
    ↓
回查 MySQL
    ↓
按距离顺序返回，并携带 distance
```

无坐标时继续走数据库分类查询；x/y 必须一起提供并校验范围。原项目按 5000 米范围搜索。修改商铺类型时，要移除旧类型的索引成员。

验收：距离由近到远、分页正确、坐标更新生效；Redis 故障不能伪装成“附近没有商铺”。

## 七、优惠券与秒杀

先创建和查询券，再同步下单，最后升级异步秒杀。

| 顺序 | 接口 | 登录要求 | 第一版 | 后面补充 |
|---|---|---|---|---|
| 1 | `POST /voucher` | 是 | 创建普通券，金额用整数分 | 完善字段约束 |
| 2 | `GET /voucher/list/:shopId` | 否 | 查询商铺有效优惠券 | 合并秒杀时间、库存信息 |
| 3 | `POST /voucher/seckill` | 是 | 事务创建券与秒杀配置 | 初始化 Redis，不覆盖实时库存 |
| 4 | `POST /voucher-order/seckill/:id` | 是 | 数据库事务同步下单 | Lua 判断、Stream 异步落单 |
| 5 | `GET /voucher-order/:id` | 是 | 查询当前用户自己的订单 | 完整状态展示 |
| 6 | `GET /voucher-order/status/:id` | 是 | 查询异步处理状态 | 失败状态、恢复与补偿 |

### 1. 同步下单

第一版必须保证：

1. 活动时间有效。
2. 使用库存大于零的条件更新，避免负库存。
3. 用户与优惠券组合唯一，保证一人一单。
4. 扣库存和插入订单在同一个数据库事务内，失败回滚。
5. 查询订单时校验归属，不能只凭订单 ID 返回其他人的订单。

先验证少量库存、多用户请求、同用户重复请求，再进入异步版本。

### 2. 异步秒杀

```text
Lua 校验时间、库存和重复购买
    ↓
预扣库存并写入 Stream
    ↓
接口返回受理订单号
    ↓
Worker 消费消息、事务落单
    ↓
提交成功后 ACK
```

资格判断、预扣和入队需要在同一脚本中协调；Lua 运行错误不会自动回滚已执行的写入，须做好参数与 key 类型预检。

后面逐项补：

- 相同订单重复消费不重复扣库存。
- Pending（已投递但未确认）消息接管。
- Worker 重启恢复、并发上限与优雅退出。
- 确定失败后的幂等补偿，重复补偿不重复增加库存。
- 数据库提交结果不确定时保留消息重试，不能立即退库存。
- 客户端轮询订单状态；失败和待处理状态可区分。

异步接口成功只表示“已受理”。浏览器处理大整数订单 ID 时用字符串模式，例如原项目的 `idAsString=true`，避免精度损失。

验收示例：80 个请求抢 7 份库存、同一用户重复下单、数据库提交后 ACK 失败、消费者重启、补偿重复执行。最终不得超卖或重复落单。

## 八、补运行能力

| 项目 | 第一版要求 | 后续完善 |
|---|---|---|
| `GET /health/live` | 返回进程存活状态，无需登录 | 接入部署探针 |
| `GET /health/ready` | 有限超时内检查 MySQL、Redis，无需登录 | 区分依赖故障 |
| 统一响应与错误 | 集中 JSON 结构、错误类型与状态码 | 与原前端契约对齐 |
| 配置管理 | 地址、TTL、上传目录、开发验证码开关 | 环境区分、禁止在源码存凭证 |
| 优雅退出 | 停止接收请求、等待后台任务、关闭连接 | 明确退出超时和消息恢复行为 |
| 接口验证 | 正常、非法输入、重复请求、依赖故障 | 并发与恢复场景 |

原项目没有实现评论、支付、核销、退款业务接口，本轮不额外扩展。已有验证码模拟也不等于真实短信服务。

## 九、每完成一步如何验收

在 `re-go-dianping` 项目根目录检查编译：

```powershell
go build ./...
```

如已有测试，再执行：

```powershell
go test ./...
```

编译通过不代表数据库、Redis 和接口行为已经验证。实际运行后按接口检查：

- [ ] 请求方法、路径、参数位置正确。
- [ ] 正常请求返回预期数据。
- [ ] 非法输入不会继续执行数据库写入。
- [ ] 不存在与系统故障返回不同错误。
- [ ] 受保护接口不带 Token 返回 401。
- [ ] 修改和查询使用当前用户身份，不能越权。
- [ ] 数据库与 Redis 的值、有效期符合预期。
- [ ] 涉及并发、异步时，重复执行与故障恢复符合约束。

近期顺序：先验收 `GET /user/:id` 和昵称流程，再写 `GET /user/info/:id`，然后写签到两个接口。每个接口跑通后再进入下一个，密码登录可在这些目标后补。
