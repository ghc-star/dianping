# 如果让你自己实现，应该怎么写

先保留接口契约和测试，暂时不要看实现。每一步先用朴素可运行版本，再加一条失败约束。下面是构建顺序，不是最终代码逐行复述。

## 1. 用户登录与会话

1. 建立POST `/user/code?phone=`，用手机号规则拒绝非法值。
2. 用crypto/rand生成6位数字，保留前导零，存Redis String，2分钟TTL。开发环境打印码，生产接短信商。
3. 增加60秒发送间隔。登录时最多5次试错，用Lua比较且删除正确验证码，防两个请求同时成功消费。
4. 根据唯一手机号查用户，不存在创建。并发创建时依赖唯一索引重新查，不能先查后插就以为没有竞争。
5. 生成随机Token，把精简ID/nickName/icon写Hash并设置30分钟TTL；不要把密码或全部用户实体放进去。
6. Auth解析Header，读Hash并续期，把DTO放Gin Context；RequireLogin检查是否存在。
7. logout真正DEL Token。再增加登录后的bcrypt密码设置；旧MD5不作为认证回退。

验证：错误码、过期码、同码重放、连续试错、两个手机号并发请求不串号、注销后旧Token失效。对照`service/user.go`与`middleware`。

## 2. 商铺Cache Aside

1. 先写Repository按ID查询，区分查无记录和DB断连。
2. Service先GET缓存，miss查询DB，成功写JSON+TTL；查无记录写短TTL空值。
3. 大量同一ID请求时加入singleflight，让同进程只做一次加载；随机TTL减少批量同时过期。
4. 多API进程用SET NX带租约争抢重建权；获取失败有上限地等待，不能递归无限重试。
5. 增加逻辑过期时间和稍长物理TTL。过期旧值可以先返回，同时有限后台刷新；cold miss仍同步回源。
6. 更新先提交DB，再失效缓存。用版本号与Lua条件写，拒绝更新前启动的旧查询在更新后回填。
7. Close取消刷新并等待，测试用loader计数控制并发时序。

验证：冷数据可读，不存在不会每次打DB，30并发只回源一次，score=0可以更新，DB错误不当成空值缓存。对照`cache/cache_test.go`。

## 3. 分布式锁

1. 生成每次加锁唯一token，`SET key token NX PX lease`。
2. 未获取到锁返回false，不把竞争当系统异常。
3. 解锁Lua先GET比较token，再DEL。不能分开GET和DEL，也不能无条件DEL。
4. 使用defer释放；用独立短超时释放锁，因为请求Context可能已经取消。
5. 模拟A租约过期、B获取新锁、A执行释放，B仍必须持有锁。

不要把锁租约当数据库约束。业务运行超过lease可能两个持有者同时工作，所以订单最终仍靠唯一索引与条件库存更新。对照`internal/lock/redis.go`。

## 4. Blog与点赞

1. 建立Blog字段与POST接口；ID、作者、点赞数由服务端控制，作者取当前用户。
2. 写热门10条查询，再批量查作者，避免每条单独查用户。
3. 加持久点赞明细表唯一(blog_id,user_id)。事务锁住Blog行，存在则删除并减计数，不存在则插入并加计数。
4. 用点赞时间作ZSet score，用户ID为member。读取最早点赞5人，再按Redis顺序重排SQL用户结果。
5. Redis只做可重建投影；中断Redis后MySQL点赞仍完整，下一次排名读取恢复。

验证：偶数次并发切换后恢复原状态，计数不为负；同毫秒按字典序处理；错误blogID不插幽灵点赞。

## 5. 关注与共同关注

1. 设计PUT目标ID/true或false，true建立关系、false删除关系。
2. 拒绝自己关注自己，验证目标存在，增加唯一(user_id,follow_user_id)。
3. 为当前用户刷新Set，成员为被关注者ID；共同关注用SINTER。
4. Redis清空后从DB恢复Set。锁多个用户时按ID排序，且先全部加锁再建立一致读取快照。

验证：重复true只一行；重复false无错误；Redis中集合被删后共同关注仍可恢复。对照`repository/social.go`。

## 6. Feed与滚动分页

1. 发布时查粉丝名单，不给未关注用户推送历史Blog。
2. 不要只在提交后写Redis：同一MySQL事务保存Blog与每位粉丝的outbox行。
3. 后台取未投递行，`ZADD feed:fanID score blogID`，成功才写delivered_at。失败下次继续。
4. 查询用最大时间戳与该时间已消费offset，按分数倒序取2条，保留Redis的ID顺序。
5. 若下一页最小score等于传入max，offset必须加传入offset；跨score才重置。
6. 保留outbox历史，重建丢失的收件箱；不仅看ready标记，也检查收件箱是否存在。

验证：同毫秒6条分3页不重复；Redis断连发布后恢复能收到；ZADD成功但未标记时重投不重复。注意迟到投递可能落在已翻过的游标之后，用户刷新第一页才能看到，不能声称离线游标是固定快照。

## 7. 签到Bitmap

1. 按配置时区获得日期，拼`sign:userID:yyyyMM`。
2. SETBIT的offset用day-1，避免把1号写到第2位。
3. BITFIELD读取本月截至今天的无符号整数uN。
4. 从最低位开始数连续1，遇0停止；今天未签就是0，不是本月累计总数。

验证：月初、时区跨日、今天缺签、月末31位。原tb_sign只是历史结构，本业务不写该表。

## 8. 附近商铺GEO

1. 保持DB经纬度权威；每个商铺类型建立一个GEO索引，member为商铺ID。
2. 启动预载，新增/更新时维护；换类型还需移除旧类型索引。
3. 校验经度和Redis纬度范围，x/y必须一起提供。
4. GEOSEARCH半径5000米、ASC、Count=page*5，截取本页再回查DB，按ID映射重排并带distance。
5. 索引暂时失败要可修复，不得静默伪装成“附近没有商铺”。

验证：无坐标走DB分类查询；有坐标距离由近到远；更新坐标后结果改变。

## 9. 优惠券

1. 普通券只写tb_voucher，金额用int64分。
2. 秒杀券验证stock、beginTime、endTime，两个表同事务写入。
3. 提交后初始化Redis资格状态，已有实时库存不能被启动预热覆盖。
4. 查询仍LEFT JOIN并筛status=1，不虚构支付/退款功能。

验证：普通券不产生Redis库存；非法时间窗不能写任何一张表；初始化失败必须能定位已创建券，按SECKILL.md恢复。

## 10. 秒杀与订单

1. 先只用Lua做资格判断：时间、库存、一人一单。用真实Redis并发测试返回码。
2. 把预扣、记录购买者、XADD、pending状态放同一脚本，预检所有KEY类型；理解脚本错误不回滚先前写入。
3. 消费组从0创建，读取`>`新消息。每条解析ID必须正整数，异常数据移死信。
4. Repository事务先查幂等订单，条件stock>0减库存，再插单；任一步失败回滚。
5. 同订单重放返回成功；不同订单但同用户券由唯一约束拒绝。并发快照造成的重复异常要在新快照查清已存在订单。
6. 只有DB提交后才标created和ACK。连接故障/未知提交结果保留Pending，不能立刻退库存。
7. XAUTOCLAIM恢复旧消费者的闲置Pending；确定性失败才原子幂等补偿，保留failed状态和死信证据。
8. 用Context和WaitGroup管理运行、停止；服务端返回受理订单号，客户端查状态确认落库。

验证：80请求争7份、同用户重复、提交后ACK失败、旧消费者宕机、确定失败补偿一次、处理未知异常仍Pending。完整原理看SECKILL.md，先理解测试断言再读脚本。
